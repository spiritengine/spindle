Research question: on Linux, how stable and unique is the (st_dev, st_ino) pair from stat(2)/fstat(2) as a primitive for proving "this fd and this pathname refer to the same underlying file object," across filesystem types and mount configurations.

Format note: plain prose, one "type: classification. finding" block per filesystem/mount type, citation URLs inline. No tables.

=== Baseline: what POSIX and Linux actually promise ===

POSIX (sys_stat.h rationale) says only: "The st_ino and st_dev fields taken together uniquely identify the file within the system," and for networked systems, "all files visible within the file tree ... on each individual processor are uniquely identified by the combination of the st_ino and st_dev fields." https://man7.org/linux/man-pages/man0/sys_stat.h.0p.html
This is a snapshot guarantee, not a persistence guarantee: it says the pair identifies a file at the moment you stat it, and says nothing about whether the same pair might later denote a different file, or whether the pair survives across time, reboots, or reconfiguration.

man7 inode(7) narrows this further: inode numbers are only guaranteed unique within one filesystem; the same number can appear on two different filesystems, which is exactly why hard links cannot cross filesystem boundaries. https://man7.org/linux/man-pages/man7/inode.7.html
So st_ino alone is never meaningful; st_dev must always accompany it, and st_dev's meaning depends entirely on what created the superblock (see the mount-namespace section below).

Central caveat that applies to every local filesystem in this survey: deleting a file frees its inode number, and ext4, XFS, and btrfs all reuse freed inode numbers from their allocation bitmaps/btrees for new files. Nothing in stat(2) itself protects against a deleted file's (st_dev, st_ino) being reassigned to a brand-new, unrelated file before your check runs. This is the textbook TOCTOU race: CERT FIO45-C notes that comparing st_ino/st_dev from lstat() and fstat() is the recommended defense against symlink-swap attacks precisely because the kernel can otherwise reuse the same device and inode for both the original and an attacker-substituted file within the race window. https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/input-output-fio/fio45-c/ and https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/posix-pos/pos35-c/
Practical implication: (st_dev, st_ino) proves identity at the instant of comparison. It does not, by itself, prove that a pathname has continuously denoted the same object since some earlier open() — an intervening delete+recreate that lands on the same freed inode number defeats it. The generation number (i_generation, exposed via NFS file handles and via ioctl FS_IOC_GETVERSION, not via plain stat) is the traditional supplement that catches this case; util-linux's mount(8) had a real CVE-class bug from skipping exactly this check. https://github.com/util-linux/util-linux/security/advisories/GHSA-qq4x-vfq4-9h9g

=== ext4 ===
ext4: (b) stable/unique only under specific conditions, not unconditionally guaranteed.
Inode numbers are unique within the filesystem while allocated, and 64-bit inode numbers are supported (the "64bit" feature, default since e2fsprogs made it standard, present since kernel 2.6.28) so overflow past 2^32 is not itself a correctness problem on modern ext4. https://man7.org/linux/man-pages/man5/ext4.5.html
The ext4(5) man page documents a specific opt-in feature, "stable_inodes" (kernel 5.5+), whose entire purpose is to mark "the file system's inode numbers and UUID as stable" — and once set, resize2fs(8) refuses to shrink the filesystem and tune2fs(8) refuses to change the UUID, because a shrink can force relocation of inodes that live past the new end of the inode table, which changes their inode numbers. This means that on a plain ext4 filesystem without stable_inodes, an offline shrink is a documented (if unusual) way for st_ino to change for a file that was never touched by the application. https://man7.org/linux/man-pages/man5/ext4.5.html
Standard inode-number reuse after deletion applies (see baseline above) — ext4 does not promise non-reuse the way tmpfs does.

=== XFS ===
XFS: (b) stable/unique only under specific configuration, and only for the file's lifetime (reuse-after-delete applies).
The default mode is inode64, "XFS is allowed to create inodes at any location in the filesystem, including those which will result in inode numbers occupying more than 32 bits." The alternative inode32 mode exists purely "for backwards compatibility with older systems and applications" that cannot handle inode numbers bigger than 32 bits, and administrators are told to opt into it explicitly if their application stack needs it. https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/xfs.rst
The two modes are mutually exclusive per mount and change what numbers XFS is willing to hand out — so "is st_ino guaranteed to fit in 32 bits" is a mount-time configuration choice, not a filesystem-format constant. Standard reuse-after-delete applies as with ext4.

=== btrfs ===
btrfs, single machine, no NFS export: (b) stable/unique only if you always compare (st_dev, st_ino) together and never st_ino alone.
btrfs, exported over NFS with multiple subvolumes: (c) not reliably unique.
btrfs gives every subvolume its own independent inode-number namespace — "a BTRFS subvolume is a part of filesystem with its own independent file/directory hierarchy and inode number namespace" — so two files in different subvolumes of the same btrfs filesystem can legitimately share an inode number. https://btrfs.readthedocs.io/en/latest/Subvolumes.html
Locally this is harmless because each subvolume also gets a distinct device number when the kernel presents it, so "even though two files on different subvolumes may have the same inode number, they will have different device numbers and are thus distinct" — the (st_dev, st_ino) pair, taken together, stays unique on the local machine. https://lwn.net/Articles/866582/
The problem is NFS export: knfsd cannot hand a client thousands of distinct device numbers (one per subvolume) over the wire, so "a Btrfs filesystem exported via NFS shows the same device number (the device number of the root) on all subvolumes" — collapsing the disambiguation that worked locally and producing real collisions; LWN reports tools like find aborting with false "filesystem loop" errors as a direct consequence. https://lwn.net/Articles/866582/
The kernel's chosen fix (per LWN's second article, discussing the "uniquifier" approach that landed after three rejected designs — internal automounts, arbitrary file handles, and raw mount options) has the NFS server XOR a kernel-internal per-subvolume "uniquifier" into the inode number before handing it to NFS clients. This explicitly does not restore a hard uniqueness guarantee: "the resulting inode numbers will still be unique within any given subvolume; collisions within a large Btrfs filesystem can still happen, but they are less likely than before." https://lwn.net/Articles/866709/
This survey did not verify the exact kernel version where the accepted "Take 4" design finally merged; treat the collision-reduction (not collision-elimination) characterization as current as of the cited LWN discussion and re-check kernel changelogs if you need a version-exact answer.

=== tmpfs ===
tmpfs: (b) stable/unique only under the inode64 configuration; (c) under inode32 or on pre-5.9 kernels sharing the global 32-bit counter.
Unlike disk filesystems, tmpfs does not reuse freed inode numbers — historically it just incremented the kernel-global get_next_ino() counter forever. The problem: that counter is a 32-bit unsigned int even on 64-bit kernels, so "it's pretty trivial to exceed 2^32 incrementations of the get_next_ino() counter if you're creating a lot of files," and once it wraps, tmpfs hands out numbers that collide with still-live older files — a real production incident (two live, different-content files reporting the identical inode number) documented by kernel developer Chris Down. https://chrisdown.name/2021/07/02/tmpfs-inode-corruption-introducing-inode64.html
The fix, merged in kernel 5.9, moved tmpfs off the shared get_next_ino() pool onto a per-superblock 64-bit counter, gated by the inode64/inode32 mount options: "Use 64-bit inode numbers" vs "Use 32-bit inode numbers." "On a 32-bit kernel, inode32 is implicit, and inode64 is refused at mount time. On a 64-bit kernel, CONFIG_TMPFS_INODE64 sets the default." inode64 "avoids the possibility of multiple files with the same inode number on a single device," at the cost that very old, non-LFS 32-bit applications may see EOVERFLOW once the counter legitimately passes 32 bits on a long-lived tmpfs. https://raw.githubusercontent.com/torvalds/linux/master/Documentation/filesystems/tmpfs.rst
tmpfs volatility (contents vanish on unmount/reboot) is not itself a caveat for this primitive: the (st_dev, st_ino) pair only needs to hold for the life of the fd, and within one mount's lifetime tmpfs numbers don't change without an actual delete+recreate. Across a reboot the entire instance — superblock, anonymous st_dev, every inode — is gone and replaced, so there is no stale pair left over to collide with; the question of "does it survive reboot" doesn't really apply since nothing survives.

=== NFSv3 ===
NFSv3: (b) stable/unique only under a 64-bit-clean client/server stack, single non-failed-over server, no re-export, and comparing fileid+fsid together (i.e., Linux's derived st_ino+st_dev), not fileid alone.
RFC 1813 defines fileid3 as a uint64 "which uniquely identifies the file within its file system" (on Unix, the inumber) — a standard, server-mandatory attribute, and Linux's NFSv3 client copies it directly into the local inode's i_ino. https://www.rfc-editor.org/rfc/rfc1813.html
The companion fsid attribute identifies the server-side filesystem/device; Linux's client uses server-address-plus-fsid as the key for constructing (and, by default, sharing) a client-local st_dev — see the sharecache discussion under mount namespaces below.
Well-known 32-bit truncation problem: a 64-bit NFS server backed by a large filesystem (e.g. XFS with inode64) can produce fileid values above 2^32. 32-bit clients, or applications not built with large-file support, then either overflow (EOVERFLOW on readdir/stat) or get silently truncated, non-unique inode numbers — this is exactly what the Linux kernel boot flag nfs.enable_ino64=0 does deliberately ("causes the kernel to return non-unique 32-bit inode numbers to all applications for all NFS mounted filesystems"), and it's also why XFS ships a server-side inode32 mount option as a mitigation. Documented on the linux-nfs list and in Red Hat Bugzilla 1003546 ("NFS + large XFS fs sometimes fails uncached lookups for client when inode number >2^32 on 32-bit computers"). https://www.spinics.net/lists/linux-nfs/msg66463.html and https://bugzilla.redhat.com/show_bug.cgi?id=1003546 and https://www.mjr19.org.uk/sw/inodes64.html
NFSv3 predates the migration/replication attributes NFSv4 added; there is no protocol-level promise that fileid or fsid survive a failover to a different, even data-identical, server.

=== NFSv4 / NFSv4.1 ===
NFSv4: (b) stable/unique only absent migration/failover, absent 32-bit truncation, and only when fileid and fsid are compared together.
RFC 7530 defines fsid as "struct fsid4 { uint64_t major; uint64_t minor; }," a REQUIRED attribute, and defines a file system itself in terms of it: "The file system is the collection of objects on a server that share the same fsid attribute" (section 1.5). This is the direct protocol analog of st_dev — fsid, not fileid, is what marks filesystem boundaries. https://www.rfc-editor.org/rfc/rfc7530.html
fileid is the direct analog of st_ino (equivalent to POSIX's inumber, unique within one fsid); RFC 7530 also adds mounted_on_fileid specifically "to allow POSIX clients to correctly construct local mounts" — i.e., to give a sane, stable st_ino for the mountpoint directory itself when one NFSv4 filesystem is grafted onto another server-side mount point, since the true fileid there would belong to the wrong fsid. https://www.rfc-editor.org/rfc/rfc7530.html
Persistent filehandles must survive server restart and migration by protocol requirement: "If the server restarts or reboots, the NFS server must honor the same filehandle value as it did in the server's previous instantiation. Similarly, if the file system is migrated, the new NFS server must honor the same filehandle as the old NFS server" (section 4.2.2). Note this guarantee is about the opaque NFS filehandle, which Linux does not expose as st_ino — it derives st_ino from the separate, weaker-guaranteed fileid attribute.
fsid persistence across migration is explicitly NOT guaranteed: the NFSv4 migration-issues draft states fsids "are only unique within a per-server context" and "would seem not to need to be persistent when file systems are moved from server to server," with a later clarification that the fsid returned during a migration event "will not necessarily be valid after resolution of the migration event." https://www.potaroo.net/ietf/all-ids/draft-ietf-nfsv4-migration-issues-14.html
Practical consequence: after an NFSv4 failover/migration to a new server, the same file's fileid may (should) stay the same, but the client's derived st_dev is allowed to change — so a naive "same (st_dev, st_ino) as before" check can spuriously report the file as different purely because of an infrastructure failover, even though the underlying object is, per protocol intent, the same file.
Re-exporting an NFS mount through a second knfsd (NFS-over-NFS) inherits all of the above problems plus its own: the Linux kernel docs on reexport describe it as workable only with careful configuration (mandatory fsid= on the export, read-only or nolock recommended, and vfs_cache_pressure=1 on the re-exporting box to avoid the client-side cache evicting filehandles that the re-export server's remote clients still depend on, which otherwise produces sporadic stale-filehandle errors). https://docs.kernel.org/filesystems/nfs/reexport.html and https://www.spinics.net/lists/linux-nfs/msg79164.html

=== CIFS/SMB ===
CIFS/SMB with serverino (default when supported): (b) stable/unique only if the whole share maps to a single underlying server-side filesystem and the app is LFS-aware.
CIFS/SMB with noserverino, or after silent fallback: (c) not reliably stable — client-generated numbers explicitly vary across remount/reboot.
SMB has no wire-protocol concept equivalent to a persistent Unix inode number the way NFS's fileid is a defined, mandatory attribute; cifs.ko's "server inode number" is a best-effort synthesis from server-provided per-file identifiers. The kernel usage docs describe serverino as using "server's inode numbers instead of generating automatically incrementing inode numbers on the client," noting that although this helps detect hardlinks and the numbers "may be persistent," the server "does not guarantee that the inode numbers are unique if multiple server side mounts are exported under a single share" — a single SMB share can be a union of several distinct underlying filesystems on the server, and their per-file identifiers are not coordinated. https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/cifs/usage.rst
noserverino generates purely client-side sequential numbers, and the doc is explicit that these "will vary after unmount or reboot which can confuse some applications." Critically, the client can fall back from serverino to noserverino automatically and silently — "when the CIFS server does not support returning inode numbers or the CIFS client detects an inode collision, the CIFS client enables noserverino option" (Red Hat KB, corroborating the kernel doc) — meaning the stability class of a mount can change mid-session without any administrator action, so code cannot assume today's behavior holds tomorrow on the same mount. https://access.redhat.com/solutions/5535561
The same 32-bit truncation family of problems applies: server UniqueID values often exceed 2^32, causing EOVERFLOW in non-LFS 32-bit applications, per the kernel usage docs.

=== FUSE-backed filesystems ===
FUSE generically: (c) not reliably stable/unique — stability is entirely delegated to the specific FUSE server implementation.
FUSE with use_ino, backed by an implementation that actually maintains persistent per-object identifiers: (b), scoped to that implementation's guarantees.
libfuse's use_ino option makes the kernel honor whatever st_ino value the userspace filesystem process reports in getattr()/readdir() replies, instead of libfuse fabricating one. https://libfuse.github.io/doxygen/structfuse__operations.html
Important nuance: even with use_ino set, libfuse and the kernel still maintain their own separate internal identifier (the "nodeid") for their own dentry/inode-cache bookkeeping; use_ino only controls what value is exposed to userspace stat() callers, and does not change what FUSE itself uses internally to recognize "is this the same file." So the framework provides a pass-through channel, not a guarantee — the actual promise (or lack of one) comes entirely from whatever backend the specific FUSE filesystem is talking to.
Concrete examples of unstable behavior: gcsfuse issue #57 documents that directory inodes are "identified only by their name, not a generation number," so deleting and recreating a directory reuses the previous inode ID without the kernel being told to forget the old one first, producing spurious EBUSY errors — a direct instance of the reuse-without-generation problem discussed in the baseline section, made worse because GCS itself has no native inode concept for (implicit) directories. https://github.com/GoogleCloudPlatform/gcsfuse/issues/57
Object-storage-backed mounts generally (rclone mount, s3fs) have no native inode concept at all — numbers are synthesized from path hashes or allocation counters — and rclone has an open feature request for configurable inode calculation specifically because its default numbers can exceed 32 bits and be unstable across listings, breaking 32-bit-only tooling. https://github.com/rclone/rclone/issues/8938
Conclusion for this category: the presence of use_ino tells you nothing about stability by itself; you must check the specific FUSE filesystem's own documentation/source for whether it derives ino from something persistent (a real backing inode, a stable content-addressed id) or from something ephemeral (a name, a listing-order counter).

=== overlayfs ===
overlayfs, default mount options: (c) not reliably stable — the kernel documentation says so explicitly.
overlayfs with xino=on (ideally combined with index=on and layers that support NFS export + UUIDs): (b), stable/unique under that specific, named configuration, with a documented overflow fallback.
The plainest "not stable" statement found anywhere in this entire survey is in the overlayfs kernel documentation itself: "st_ino will only be unique when combined with st_dev, and both of these can change over the lifetime of a non-directory object." https://raw.githubusercontent.com/torvalds/linux/master/Documentation/filesystems/overlayfs.rst
The mechanism is copy-up: a file that's only ever been read reports an st_dev/st_ino sourced from whichever lower or upper filesystem is actually backing it at that moment; the first write to it triggers a copy from the read-only lower layer to the writable upper layer, and from then on stat() reports the upper filesystem's numbers instead — a silent, application-invisible identity change for a file the application never renamed or recreated itself. Directories are exempted from this instability (they consistently report overlayfs's own st_dev), but non-directory objects are not, by default.
The xino feature exists specifically to fix this: it "composes a unique object identifier from the real object st_ino and an underlying fsid number," packing the small per-layer fsid index into the high bits of the reported inode number "because the underlying filesystems rarely use the high inode number bits" — making the exposed number layer-independent and therefore copy-up-stable. It's enabled with the "xino=on" mount option (or "xino=auto," which enables it only when overlayfs can additionally guarantee persistent st_ino for that mount, or via the module parameter xinoauto=on, or CONFIG_OVERLAY_FS_XINO_AUTO=y at build time). If a particular underlying inode number is too large to leave room for the fsid bits, overlayfs falls back to the old, unstable behavior for that one inode and continues — so xino=on is a strong statistical improvement, not an absolute per-file guarantee, on filesystems with very large native inode numbers. https://raw.githubusercontent.com/torvalds/linux/master/Documentation/filesystems/overlayfs.rst
The separate index option is what makes xino's promise hold across repeated copy-ups rather than just the transition itself: it records each upper-layer copy's lower-layer origin (an NFS file handle plus the lower filesystem's UUID) in a trusted.overlay.origin extended attribute, letting overlayfs recognize "this upper object already corresponds to that lower object" and reuse the same composed identifier consistently. index=on requires the lower filesystem to support NFS export and carry a valid UUID, and the upper filesystem to support extended attributes — an overlay mount will fail outright with EOPNOTSUPP if those requirements aren't met, which is itself useful: it means you cannot silently end up in a half-working index configuration.

=== Bind mounts ===
Bind mounts: (a) guaranteed identical by construction — the one unconditional "yes" in this whole survey.
A bind mount (MS_BIND) does not create a new filesystem instance; it attaches the existing subtree at a second path, and "the bind mount has the same mount options as the underlying mount" (man mount(2)). https://man7.org/linux/man-pages/man2/mount.2.html
Mechanically, this means no new superblock is created and no new device number is allocated for the alias — a bind mount is just a second vfsmount pointing at the same dentry/inode/superblock the original mount already uses (the get_anon_bdev allocation path, discussed below, is only reached from a filesystem driver's own mount/fill_super routine, which a bind mount never re-enters). So st_dev and st_ino read through a bind-mounted path are byte-for-byte identical to reading them through the original path — on the same host, regardless of which mount namespace either path is visible in.
One practical corollary, confirmed by discussion threads on detecting mount points via stat: this identity is exactly why bind mounts of a source on the same filesystem are invisible to "walk the tree and look for an st_dev discontinuity" mount-detection logic — you need /proc/*/mountinfo, not stat(), to enumerate bind mounts. That's a feature of this guarantee, not a counterexample to it.

=== Two mount namespaces/containers independently mounting the same underlying filesystem ===
This is not really a mount-namespace question; mount namespaces only control which mounts are visible and how they're named, not superblock identity. What determines whether two mounts share an st_dev is entirely whether the two mount operations end up sharing one superblock — and that answer differs by filesystem type. Classification below is per-mechanism, not a single blanket answer.
Mechanism: filesystems without a real block device (tmpfs, overlayfs, NFS, most FUSE filesystems, procfs, etc.) get a fresh anonymous device number allocated once per new superblock instance via get_anon_bdev(), called from that filesystem's own mount path. https://www.rpmfind.net/linux/rpm2html/search.php?query=kernel(get_anon_bdev) (kernel doc-comment summary; canonical source is fs/super.c in the kernel tree) Superblocks are global, namespace-agnostic kernel objects — mount namespaces just hold references into a shared pool of them.
Bind mount of the same host directory into two containers/namespaces: (a) — per the bind-mount section above, no new mount operation into the filesystem driver ever happens, so both containers see identical st_dev and st_ino. This is the common Docker/Kubernetes hostPath / bind-mount-volume pattern, and it preserves the primitive perfectly.
Two independent real NFS mounts of the same export from two different namespaces/containers, default options: (b), stable/unique only under matching mount options and consistent server addressing. The Linux NFS client deliberately implements cross-mount superblock sharing keyed by server identity plus fsid — nfs(5) states plainly that "If neither option is specified, or if the sharecache option is specified, then a single cache is used for all mount points that access the same export," and only "if the nosharecache option is specified" does a mount point get an independent cache/superblock. https://man7.org/linux/man-pages/man5/nfs.5.html Because superblocks aren't namespaced, this sharing happens even when the two mount() calls originate in two unrelated mount namespaces — so by default, two containers independently NFS-mounting the same export do get the same st_dev, and the primitive holds. It breaks if either mount specifies nosharecache, or if the two mounts address the server differently (e.g. one by hostname, one by IP, or through different DNS results) — a known sharp edge raised on the linux-nfs list, where mount's own duplicate-mount detection was noted to fail for exactly this reason.
Two independent mounts of the same block device (ext4/xfs/btrfs on a real partition) from two namespaces: expected to reuse the one live superblock and get the same st_dev, because the kernel's block-device-backed mount path looks up an existing superblock by the block device itself before creating a new one; recent util-linux even restricts re-mounting an already-mounted block device partly to avoid two independent superblocks racing on one device. This was not found stated as a single explicit "same st_dev guaranteed" sentence in kernel docs, so treat it as (b)/inferred-from-mount-architecture rather than a directly cited guarantee, and verify empirically if it's load-bearing.
Two independent overlayfs mounts with identical lowerdir/upperdir, or two independent tmpfs mounts, from two namespaces/containers: (c) — no cross-mount superblock-sharing mechanism for these filesystem types was found in any source consulted here, so each mount() call gets its own fresh get_anon_bdev() allocation and thus its own distinct st_dev, even though the visible content is identical. This is the inverse failure mode from the btrfs/NFS cases above: instead of one st_dev wrongly appearing to cover two different underlying files (a false positive for "same file"), you get two different st_dev values wrongly appearing to rule out sameness for what is, in every content sense, the same file (a false negative). Since tmpfs's post-5.9 inode counter is also per-superblock, even the st_ino sequence differs between the two mounts.
Bottom line for this category: "different container/namespace, same physical filesystem" does not have one answer. Bind-mounts and NFS-with-matching-sharecache preserve st_dev identity across namespaces by kernel design; independent overlayfs/tmpfs/most-FUSE mounts of "the same" content do not, and there is no configuration flag that makes them do so — the content has to actually flow through a shared superblock (i.e., be a bind mount or a protocol with explicit superblock-sharing like NFS) for the primitive to survive being mounted twice.

=== Summary table (prose form, not a markdown table, per formatting instructions) ===
ext4: (b), configuration-dependent (stable_inodes feature, absence of shrink), plus universal reuse-after-delete caveat.
XFS: (b), configuration-dependent (inode32 vs inode64), plus universal reuse-after-delete caveat.
btrfs, local: (b), safe only as (st_dev, st_ino) pair, never st_ino alone, across subvolumes.
btrfs, NFS-exported: (c), documented, only-reduced-not-eliminated collision risk across subvolumes.
tmpfs: (b), configuration-dependent (inode64 vs inode32/pre-5.9 kernels); not reused within one mount's life; moot across reboot since nothing survives.
NFSv3: (b), configuration/scenario-dependent (64-bit-clean stack, no failover, no re-export).
NFSv4: (b), configuration/scenario-dependent (no migration/failover, no 32-bit truncation); fsid explicitly allowed to change across migration even though fileid should not.
CIFS/SMB: (b) under serverino with a single backing filesystem and an LFS-aware app; (c) under noserverino or after silent client fallback.
FUSE generic: (c); becomes (b) only per specific backend implementation that documents persistent ino assignment.
overlayfs default: (c), explicitly documented as changeable across copy-up.
overlayfs with xino=on (+ index=on): (b), named configuration, with a documented per-inode overflow fallback to the unstable behavior.
Bind mounts: (a), unconditional, true by construction, unaffected by mount namespace.
Cross-namespace/container same filesystem: no single answer — (a) for bind mounts, (b) for NFS under matching sharecache/addressing, (c) for independent overlayfs/tmpfs/FUSE mounts of the same content.
